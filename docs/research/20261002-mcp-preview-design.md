# Reusable Fulcra MCP PR previews: design research

Research date: October 2, 2026. Authenticated GitHub source and current Google documentation were inspected. This proposes team infrastructure for testing changes to `fulcradynamics/fulcra-context-mcp`, with AICQ as an initial consumer. No application code, cloud configuration, secrets, or remote services were changed. Research records were saved in the repository and canonical Fulcra workspace.

## Answer

Josh's Portal preview **pattern** can test a new Fulcra MCP build. The current Portal workflow itself cannot do that: it selects the Portal PR's image, configures Portal variables, and targets `dev-portal`. Reuse its exact-commit CI gate, digest deployment, no-traffic revision tags, authorization, and deployment receipts; give MCP its own service configuration, OAuth identity/base URL, state isolation, ingress, tests, and cleanup.

A dedicated **MCP preview Cloud Run service**, separate from normal dev MCP, is the cleaner reusable team facility. Tagging revisions on the existing dev MCP service is technically a candidate, but requires explicit changes to ingress and deployment permissions, separate OAuth state per preview, and coordination with normal dev service deployment/configuration. Tags alone isolate routing; they do not define an isolated runtime identity, bucket, or service policy.

## What Portal's machinery actually does

1. **Trusted control workflow.** `/preview <environment>` comments on an open PR trigger the deployment workflow from the default branch. The workflow checks active `fulcradynamics/eng` membership before accessing an environment. It accepts an exact single command, verifies target/config environments exist, then maps all preview commands to `PREVIEW_TARGET=dev` and revision tag `pr-<number>`. `/preview dev` uses dev API configuration; `/preview prod` uses production API configuration on the dev preview service. [Trigger and authorization](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/deploy.yml#L3-L113).
2. **Exact PR-head image.** CI checks out the PR head rather than GitHub's synthetic merge SHA and publishes `pr-<number>-<short-head-sha>`. Deployment resolves the current PR head, checks its successful `ci.yml` pull-request run, resolves that tag to an image digest, and deploys the digest. The retained receipt associates the full head SHA with the deployment. Current CI's build depends on lint, not a test job; the deploy workflow's comment saying "needs test" is stale. MCP should use its actual test matrix, rather than transplant this lint-only gate. [CI source/ref and build dependency](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/ci.yml#L15-L78), [deploy gate and digest](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/deploy.yml#L186-L245).
3. **Target separate from runtime config.** One job reads `FULCRA_ENVIRONMENT`, `PUBLIC_AUTH0_DOMAIN`, `PUBLIC_AUTH0_CLIENT_ID`, and `PUBLIC_FULCRA_API_ENDPOINT` from the chosen configuration environment. Deployment reads `GCP_PROJECT_ID`, `GCP_REGION`, and `CLOUD_RUN_SERVICE` from the target environment, then sets all four selected runtime variables explicitly. This avoids carrying prior preview backend overrides into the next deploy. These particular variable names and settings are Portal-specific. [Config job](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/deploy.yml#L125-L160), [target and env update](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/deploy.yml#L250-L273).
4. **Tagged no-traffic deployment.** Preview deployment adds `--no-traffic --tag pr-<number>`, retrieves the returned tagged URL from `.status.traffic`, and publishes it in GitHub deployment status. It does not route the main service URL to the preview. A subsequent preview for that PR moves its tag to the new revision. [Deploy and URL receipt](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/deploy.yml#L269-L297).
5. **Existing operational evidence.** [PR227](https://github.com/fulcradynamics/portal/pull/227) contains `/preview prod` commands and a tagged URL. [Run36909562519](https://github.com/fulcradynamics/portal/actions/runs/36909562519), October 1, 18:48 UTC, succeeded with a "Preview on dev (prod config)" job; [run36892216689](https://github.com/fulcradynamics/portal/actions/runs/36892216689) also succeeded. This proves Portal's deployment workflow operates, not that MCP OAuth or state works on tagged URLs.

## What must change for Fulcra MCP

| Piece | Current source | Reusable MCP change |
|---|---|---|
| Build/test | Portal Node24 + Font Awesome build secret; MCP already tests locked and latest-SDK dependencies | Keep MCP Python/Docker build and both MCP test lanes; build an exact-head candidate only after the required checks pass |
| Image lookup | Portal-specific Artifact Registry path and tag convention | MCP-specific path; ensure the build's naming matches the deploy lookup; record full SHA and digest |
| Deploy authorization | Active eng member, GitHub app membership lookup, target/config environments | Reuse the trusted default-branch controller and explicit approval gate; add the MCP environment/service permissions |
| Runtime variables | Portal `PUBLIC_*` values | `OIDC_SERVER_URL`, `OIDC_CLIENT_ID`, `FULCRA_OIDC_DOMAIN`, `FULCRA_API`, `STATE_PATH`, logging and the HTTP listening settings |
| Reachability | Portal module `public=true` permits direct run.app ingress | Make the MCP preview URL externally reachable while retaining MCP OAuth; do not assume the existing dev MCP ingress permits tagged direct URLs |
| Identity/state | Portal cookies/API config; MCP one shared `/clients` bucket | Separate preview issuer/resource configuration and durable state namespace; validate callback and account isolation before acceptance |
| Cleanup | Remove one tag and delete PR images | Also retire preview OAuth/state/URL registrations with a defined retention policy; coordinate close/build/deploy cleanup |

Its repository IaC currently has public visibility and team access but **no environment/image variables** matching Portal's workflow. [MCP repo config](https://github.com/fulcradynamics/infrastructure/blob/4f26f9560299a177129d56932739cb6e83c00bde/tf/github/repos/fulcra-context-mcp/terragrunt.hcl#L11-L26), [Portal repo config](https://github.com/fulcradynamics/infrastructure/blob/4f26f9560299a177129d56932739cb6e83c00bde/tf/github/repos/portal/terragrunt.hcl#L25-L49).

The existing MCP module is pinned to older commit `4128cfc6c3d512578f5f81d7a877dc2a7b9f1d86`. It hardcodes `service_name=mcp`, internal/load-balancer ingress, one client-state GCS mount, and the runtime map described above; it does not pass the newer `github_deployers` setting. It needs extension or a preview service module rather than a Portal-specific environment-only edit. ## Federation: copying Portal authentication will fail for public MCP

The current Google workload-identity provider admits only **private** repositories owned by Fulcra. MCP is public. This is an explicit IaC restriction, so copying Portal's `google-github-actions/auth` step will not produce a usable federation path for the public MCP repository. [Provider condition](https://github.com/fulcradynamics/infrastructure/blob/4f26f9560299a177129d56932739cb6e83c00bde/tf/gcp-projects/projects/fulcra-github/main.tf#L14-L29).

Simply removing the private-repository condition has a larger consequence: Artifact Registry's services repository grants `roles/artifactregistry.repoAdmin` to the provider's entire Fulcra owner-ID principal set. That binding currently relies on the private-only admission rule. A public-MCP route should be a separately approved, narrowly scoped provider/pool and repository-specific publishing/deployment bindings, rather than widening that condition in place. [Registry binding](https://github.com/fulcradynamics/infrastructure/blob/4f26f9560299a177129d56932739cb6e83c00bde/tf/artifacts/repositories.tf#L50-L56).

The reusable Cloud Run module grants deployment by exact repo/environment subject, with `roles/run.developer` on the service and `roles/iam.serviceAccountUser` on its runtime account. These are separate from Artifact Registry publish/read permissions. [Deployer IAM](https://github.com/fulcradynamics/terraform-modules/blob/70cd3cf04c36ae768057b9f76b59a71e0d44ea2c/cloudrun_service/iam.tf#L61-L84).

An alternative is a trusted private deployment-controller repository that selects and records the explicit public MCP PR SHA/digest. That controller must keep untrusted PR build execution separate from its publish/deploy credentials; putting the controller in a private repo does not make arbitrary PR Docker/build code trusted. This is a design option, not an observed existing Fulcra workflow.

## Existing dev service versus a dedicated preview service

**Existing dev MCP, tagged revisions:** could minimize initial provisioning if Josh approves direct/public preview ingress or explicit load-balancer routing, configures deployer IAM, separates each preview's state/issuer, and coordinates normal dev deployment. It retains the service's runtime identity, bucket permissions, settings inherited by revisions, and maintenance policy. The current source gives it shared `/clients` state and ingress through a load balancer, so Portal's direct tag-URL behavior cannot be assumed. A dedicated `STATE_PATH` subdirectory is an application separation, not an IAM boundary from a revision able to access the same bucket.

**Dedicated MCP preview service:** keeps experimental source, deploy permissions, runtime account, and OAuth state outside the normal dev endpoint. It can reuse Cloud Run, Artifact Registry, the existing infrastructure PR/apply process, and Portal's deployment mechanics. A single shared preview service still requires per-PR state/issuer separation and close/deploy coordination; stronger isolation can use one service and state bucket per PR at additional lifecycle cost. The deployment facility should serve Fulcra MCP contributions generally, with AICQ a first consumer rather than its sole reason to exist.

The shared Cloud Run module also declares 100% traffic to `LATEST`; its lifecycle ignores container-image changes but not traffic. Before mixing `--no-traffic` preview revision management and OpenTofu applies on the same service, inspect an actual plan and define traffic ownership. The source identifies the possible ownership conflict; this research did not observe an apply changing traffic. [Traffic and lifecycle config](https://github.com/fulcradynamics/terraform-modules/blob/70cd3cf04c36ae768057b9f76b59a71e0d44ea2c/cloudrun_service/main.tf#L159-L171).

## Cleanup and concurrency improvements

The deploy job serializes by target with `cancel-in-progress=false`, reducing deploy-versus-deploy races. CI cancels prior builds for the same PR. Close cleanup shares **CI's** group to cancel a build, then removes the preview tag and deletes PR images. Image deletion protects digests with non-PR tags by removing only the matching PR tags. [Deploy concurrency](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/deploy.yml#L162-L181), [close cleanup](https://github.com/fulcradynamics/portal/blob/ac40b9b7e9c85af370d309504104ba22ca038418/.github/workflows/pr-cleanup.yml#L3-L77).

Source-level gaps to address in the MCP adaptation:

- Close cleanup does not share the deploy concurrency group. A previously admitted or queued deploy can still publish a tag after cleanup. Recheck PR-open status and selected SHA immediately before deployment, and coordinate cleanup with that same lifecycle lock.
- The two cleanup jobs have no `needs` dependency: image deletion and tag removal can run in parallel. Sequence them deliberately and record partial failures rather than assume removal happens before deletion.
- Removing a tag does not explicitly delete the Cloud Run revision or its OAuth state. Define retention and credential-state cleanup, and protect any revision/state still required by another active preview.
- Use full SHA in build provenance and receipts; the current image locator uses a seven-character SHA tag. Digest pinning prevents later tag movement after resolution but does not, by itself, verify who built the image or that the digest came from that CI candidate.
- Do not treat successful deployment as successful MCP evaluation. Add post-deploy discovery/unauthenticated denial, authenticated tool access, distinct-account isolation, refresh/restart, and host UI checks as separate gates.

These are deductions from workflow source, not failures reproduced on Fulcra's preview service.

## MCP transport, OAuth, and state

Cloud Run explicitly supports remote Streamable HTTP MCP servers. Tagged revisions have directly addressable HTTPS URLs even with zero default traffic allocation. This validates the deployment technique, subject to the service's ingress/authentication policy; it does not validate our OAuth implementation. [Google MCP hosting](https://docs.cloud.google.com/run/docs/host-mcp-servers), [tagged revision testing](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration#tags).

The current MCP server uses `stateless_http=True`, listens on `0.0.0.0` in HTTP mode, and mounts `/mcp`. It rejects the optional GET SSE endpoint; this does not rule out POST Streamable HTTP responses. Set HTTP mode and the listening port to match the Cloud Run container configuration, rather than leave the stdio/4499 local defaults implicit. [Transport](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/main.py#L58-L65), [mount and listener](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/main.py#L294-L324), [settings](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/settings.py#L6-L18).

OAuth needs two distinct redirect relationships: the MCP client's redirect back to its own host, and the MCP server's upstream Fulcra/Auth0 callback. The server derives the latter as `OIDC_SERVER_URL + /callback`, and uses that exact URI for both authorization and code exchange. Its issuer/resource metadata must agree with the externally used MCP origin. A PR tag URL cannot simply inherit the ordinary dev server's base URL. Register an explicitly allowed upstream callback for the test origin; do not propose an unrestricted wildcard for every run.app service. The initial spike found the production MCP client already permits the particular loopback callback rejected by the separate SDK client; a real exchange remains unverified. [Upstream callback construction and exchange](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/provider.py#L339-L420), [resource metadata](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/main.py#L92-L103), [existing callback allowlist](https://github.com/fulcradynamics/infrastructure/blob/4f26f9560299a177129d56932739cb6e83c00bde/tf/prod/auth0/apps.tf#L284-L351).

**Stateless MCP transport does not mean stateless OAuth.** The current provider persists established registrations/grants/tokens, but keeps pending login state, authorization codes, and credentials awaiting token exchange only in process dictionaries. A callback or token exchange routed to another process can therefore lose the pending transaction; a restart can also lose it. This is a source-level failure mode, not a reproduced production incident. [In-memory state](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/provider.py#L95-L112), [callback and code lookup](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/provider.py#L368-L420).

Google documents cookie-based session affinity as best effort; it cannot guarantee the same process after scaling or termination. In this OAuth flow, the browser and MCP host are also separate HTTP clients, so browser affinity would not establish that the host's token exchange reaches the same process. [Session affinity](https://docs.cloud.google.com/run/docs/configuring/session-affinity).

Refresh serialization is a `threading.Lock` within one process, and grant persistence uses JSON file writes. The deployment mounts a shared GCS bucket as `/clients`. Google documents that this filesystem mount has no file locking and that concurrent replacements can lose earlier writes. Turning off metadata caching does not supply cross-process locking or atomic token rotation. Before claiming multi-instance safety, use durable, expiring, single-use OAuth transactions and coordinate grant updates across instances, with a storage backend that supports conditional/transactional writes. The particular backend is unselected. [Grant lock/write implementation](https://github.com/fulcradynamics/fulcra-context-mcp/blob/9efe894e15ebb612298e41341a232e713c459505/fulcra_mcp/provider.py#L134-L155), [mounted bucket and runtime IAM](https://github.com/fulcradynamics/terraform-modules/blob/4128cfc6c3d512578f5f81d7a877dc2a7b9f1d86/services/mcp-service/cloudrun.tf#L13-L47), [Google volume limitations](https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts#limitations).

A low instance cap can constrain an initial manual smoke test, but cannot substitute for this evaluation: Google says maximum-instance settings can be briefly exceeded, and tagged zero-traffic revisions are not necessarily counted toward the service-level cap. [Instance limits](https://docs.cloud.google.com/run/docs/configuring/max-instances). PR revisions must not receive the normal dev or production credential bucket. Namespace separation within a bucket helps organize data; a revision with whole-bucket IAM can still access other prefixes.

## Recommended first version and division of work

Michael clarified two goals: AICQ should provide a vertically focused agent-connection experience on a Fulcra backend; separately, this work should improve Fulcra's reusable agent-first development and CI/CD. Customer dashboard/app publication through Vercel and internal MCP testing are related uses of Fulcra, but have different deployment requirements. The MCP preview contribution should remain reusable in the separate Fulcra MCP work, rather than be designed solely around an AICQ tunnel.

Start with **one reusable MCP test service at a stable approved HTTPS hostname, one selected candidate at a time**. This is a recommendation, not a recorded hosting choice. It preserves a stable upstream callback and host installation URL while testing different exact PR commits. Reuse the Portal trusted comment controller, successful candidate checks, image digest, deployment receipt and cleanup pattern. Add the MCP-specific variables, scoped federation, runtime identity and isolated test credential storage. Agree on whether test configuration points to dev or production Fulcra; AICQ's owner harness lives in production and cannot be assumed to exist in a dev account. Use designated test accounts and record their actual identities.

Then add concurrent PR-tag URLs if needed. Each needs matching issuer/resource/callback configuration, state isolation and lifecycle control. Retagging a URL while login is in flight also needs a deliberate version/state policy. Choose one service per PR if the requirement is an IAM boundary between candidates; revision tags alone cannot provide it.

| Work | Where it belongs |
|---|---|
| Approve public-repository federation or a private trusted controller; scoped registry/run/runtime bindings | Josh's infrastructure review and existing IaC apply process |
| Bootstrap reusable test service, reachable hostname, Auth0 client/callback and isolated state identity/storage | Josh/Fulcra/GCP infrastructure; related service configuration using existing modules |
| Adapt command workflow, required MCP CI lanes, digest/SHA receipts and coordinated cleanup | Reviewable MCP/infrastructure contribution using the existing pattern |
| Make pending OAuth transactions and refresh updates safe across processes | Reusable MCP provider work, with separate evaluation |
| Verify real ChatGPT/Codex linking, tools and account boundaries against the deployed candidate | Live host acceptance, separate from CI/deployment success |

The minimal request to Josh is a **closely related MCP test deployment facility**: reuse Cloud Run and the established controller, but supply MCP service/state/auth configuration and a narrowly scoped path from its public repository. Overwriting normal dev MCP may save initial provisioning, but requires confirming its use/traffic ownership and accepting shared-service consequences; that was not authorized or performed here.

Acceptance should bind the actual URL, full SHA, image digest, configuration identity and tested host versions. Check discovery, unauthenticated denial, OAuth linking and a real tool call; test two distinct owners and wrong-resource denial; test refresh, reconnect/restart and cross-instance pending-login behavior. Add close-during-deploy and cleanup failures. Keep each result separate. A successful preview deploy cannot complete AICQ M2 without its required ChatGPT rendering/linking and fresh-account setup checks.

## Limits of this spike

Source and successful Portal Actions establish the pattern and configuration gaps. This pass did not inspect live GCP IAM/service state, perform an OpenTofu plan, register callbacks, deploy MCP, or verify a live preview's authentication. The WIF, ingress, traffic-ownership and OAuth-state conclusions are based on the pinned source and current provider documentation. No milestone attempt was started; M2's final retry remains unused.
